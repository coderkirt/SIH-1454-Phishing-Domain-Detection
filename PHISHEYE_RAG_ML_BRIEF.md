# PhishEye — brief for RAG and ML planning

Paste this into Claude. It describes the live system only. Do not assume a trained model, a vector database, or labelled accuracy numbers. None of those exist in the repo.

## What it is

PhishEye is a software-only phishing checker: a React web console, a FastAPI service, a SQLite file, and a Chrome extension (Manifest V3). A user submits a URL, pastes an SMS/WhatsApp/email, or uploads a QR image. The service returns a 0–100 score, a level, a plain-language Simple View, and a Technical View. The extension scans a link before the page opens.

There is **no trained classifier** (no scikit-learn, TensorFlow, PyTorch, or joblib file). The field called `ml_score` / `ml_probability` is a copy of the lexical/heuristic URL score. It is not a model probability.

## Stack

- Python 3.12, FastAPI, Uvicorn, Pydantic, SQLite (`sqlite3`, file `backend/threats.db`)
- Auth: bcrypt + JWT (`python-jose`)
- QR: OpenCV, Pillow, NumPy
- React 19, Vite 8, Tailwind 4, Axios, Recharts
- Chrome extension MV3, version 1.8.0
- Feeds over HTTP: OpenPhish, URLhaus, PhishTank, Phishing Army; Google Safe Browsing only if an API key is set
- Tests: pytest. No dataset CSV/JSONL in the repo.

## How a decision is made today

1. Normalize the URL. Unwrap shorteners only after blocking fetches to localhost, private IPs, and cloud metadata.
2. URL/domain heuristics: lookalike brand, suspicious words (verify, login, password, OTP), raw IP, long URL, many subdomains, suspicious TLD (`.xyz`, `.tk`, …), domain missing, domain age under 30/90 days, missing HTTPS, bad TLS, brand name on a free host.
3. Threat-feed lookup. Outcomes are match, no match, or unavailable. A miss is not “safe”.
4. Message rules (English + Hinglish), fixed points: urgency 12, fear 12, authority 12, coercion 10, financial pressure 10, credential/OTP 14, countdown 8, greed bait 10, secrecy 8, emotional manipulation 10.
5. Optional: community marks, sender hints, popup-style page clutter.
6. Combine.

**Single URL:** `score = max(heuristic, feed floor)`. Floors: exact URL 85, normalized URL 80, hostname 72, registered domain 55. An unverified feed report floors at 58. Heuristics cannot cancel a confirmed feed hit.

**Several links in one message:** weighted fusion (sums to 1.0):

| Signal | Weight |
|---|---|
| URL structure | 0.22 |
| Domain | 0.16 |
| Lexical score (`ml` slot) | 0.10 |
| Message language | 0.10 |
| Psychological cues | 0.10 |
| Threat intelligence | 0.10 |
| Brand impersonation | 0.08 |
| Sender | 0.05 |
| Community reports | 0.05 |
| Redirects | 0.04 |

Wording alone is capped at 35. Levels: LOW 0–29 (extension opens), MEDIUM 30–49 (asks), HIGH 50–69 (blocks), CRITICAL 70–100 (blocks). If the API is down, the extension blocks (“unknown is not safe”). `localhost` and `127.0.0.1` are forced LOW; other raw IPs are still suspicious.

Code: `backend/app/services/url_checker.py`, `decision_engine.py`, `risk_engine.py`, `psychology.py`, `threat_intel.py`.

## Data already stored (SQLite)

- `url_checks`: url, risk_level, risk_score, ml_confidence, user_id, timestamp
- `content_scans`: source_type, url, risk_level, risk_score, scam_risk, confidence
- `extracted_links`: scan_id, url, domain, risk_score, classification
- `user_reports`: url, domain, user_label (scam / risky / safe), reason
- `domain_reputation`: scam_reports, risky_reports, safe_reports
- `scan_feedback`: scan_id, helpful
- `threats`: feed snapshot rows (threat_type, threat_data, severity)
- `users`: username, email, password hash

These rows are **product history**, not a balanced labelled training set. User labels are opinions. Feed hits are the strongest labels, and only for URLs that were queried.

## What is missing for ML and RAG

- No labelled phishing/legitimate dataset in the repo
- No train/validation split, no precision/recall/F1
- No embeddings, vector store, or document chunker
- No page-body crawl of arbitrary sites (QR bytes are decoded in memory and not saved; the scanner must not fetch private-network URLs)
- Explanations are generated by code (`warnings.py`), not retrieved from a knowledge base

## Constraints any design must keep

- A confirmed threat-feed match must not be overruled by a model.
- Psychology-only text must not reach HIGH/CRITICAL by itself.
- Unavailable feeds and API errors stay “not safe”, not “clean”.
- Do not store passwords, OTPs, or inbox contents. The extension does not read form fields or cookies.
- Loopback addresses stay local-dev exceptions. Do not mark all private IPs safe.

## Ask Claude to design (not to invent metrics)

1. **Supervised URL/message model.** Features already computed by the heuristics (lexical URL, domain age, TLS, brand, redirect hops, psychology category points, feed status). Proposed label sources: PhishTank/OpenPhish positives, a legitimate URL list (for example Tranco top sites), plus later `user_reports` only as a weak extra signal. Train/test split, leakage rules (same domain must not sit in both sets), and where the probability plugs in: the existing `ml` fusion weight 0.10, still under the feed floor. Report precision, recall, and F1 only after a real held-out run.
2. **RAG, as an explainer, not as the scorer.** Retrieve short chunks (feed provider notes, psychology pattern definitions, past similar `user_reports` / scan reasons) to write the Simple View. The numeric score stays with the decision engine. Say which store fits this app (local SQLite is the live DB; a vector index would be new), what to embed, and what must never be retrieved (password hashes, raw QR images, private user text beyond what the user submitted for that scan).

Public starting points that are real, not in this repo: UCI Phishing Websites dataset (id 327); PhishTank; OpenPhish; APWG trend reports.
